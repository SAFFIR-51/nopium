# NPIUM

병원 환자 연계, NPIUM 최종 매칭 통제, 방문 기록, 월간 리포트 제공과 병원 진료 반영을 연결하는 앱입니다. 체험 모드와 로컬 서버 모드를 분리했습니다.

## 실행

Node.js 24 이상을 사용합니다. 로컬 DB는 Node 내장 SQLite를 사용하므로 별도 DB 설치가 필요 없습니다.

### 체험 모드

```powershell
npm install
npm run dev
```

기존과 같이 헤더에서 역할을 선택합니다. 예시 데이터는 브라우저의 `npium-care-preview-v1`에 저장됩니다. 서버 계정이나 DB와 합쳐지지 않습니다. 빌드는 `npm run build`, 실행은 `npm start`입니다.

### 로컬 서버 모드

```powershell
npm run local:account
npm run local:dev
```

첫 명령에서 관리자 계정 ID·이름·비밀번호(12~128자)를 직접 정합니다. 비밀번호는 터미널에서 숨겨 입력하고 서버에는 salt와 scrypt 해시만 저장합니다. 기존 계정을 덮어쓰지 않습니다. 관리자 로그인 후 `/admin/accounts`에서 병원·치료사·환자 계정을 생성하고 환자·보호자 계정을 연결합니다.

서버는 기본 `http://127.0.0.1:3100`에서 실행됩니다. `/login`으로 로그인합니다. 빌드 후 실행하려면 다음 명령을 사용합니다.

```powershell
npm run local:build
npm run local:start
```

- 기본 DB: `.local/npium.sqlite`. 예시 환자가 없는 빈 DB로 시작합니다.
- `NPIUM_DB_PATH`로 DB 파일을 지정할 수 있습니다. 상대 경로는 프로젝트 폴더 기준입니다.
- `PORT`로 포트를 지정할 수 있습니다.
- `local:*` 실행 명령은 `NEXT_PUBLIC_DEMO_MODE=false`를 설정합니다. 빌드 결과는 `.next-local`에 두므로 체험 모드의 `.next`와 분리됩니다.
- CLI 자동화가 필요하면 `NPIUM_ADMIN_USERNAME`, `NPIUM_ADMIN_NAME`, `NPIUM_ADMIN_PASSWORD`를 해당 프로세스 환경에 전달할 수 있습니다. 비밀번호를 소스나 명령 이력에 적지 않습니다.
- 실제 서버 계정의 역할·소속은 서버에서 검증합니다. 브라우저의 체험 역할 값으로 바꿀 수 없습니다. 세션은 HttpOnly/SameSite 쿠키와 DB로 관리하며 로그아웃·계정 비활성화 시 폐기합니다.

## 역할별 흐름

| 역할 | 화면과 처리 |
| --- | --- |
| 병원 | `/hospital` 환자 연계·진행, `/hospital/approvals` 재활 처방 변경안 저장·승인, `/hospital/reports` 제공본 확인·외래 재평가·승인 연결, `/hospital/linkage` 지역사회 연계 |
| NPIUM | `/admin` 운영 현황, `/admin/assignments` 제안→치료사 응답→최종 매칭 확정·조정, `/admin/progress` 환자별 원기록·평가·보고·병원 진료 및 현장 반영 이력 |
| NPIUM | `/admin/analysis` 병원·치료사·월별 통계와 취합·제공·정정본, `/admin/providers` 치료사 인증 및 등록·보험·등급·배정 보류, `/admin/quality` 월간 평가·만족도, `/admin/billing` 계약·청구·조정, `/admin/accounts` 계정·소속·환자 연결·최근 서버 처리 이력 |
| 치료사 | `/expert` 일정, `/expert/requests` 매칭 응답, `/expert/patients/[id]` 초기·중간·종료 평가 및 회차 기록·정정, 승인 버전 확인, 월간 소견 저장 |
| 환자·보호자 | `/my` 연결 대상, `/my/requests` 신청, `/my/schedule` 일정 요청, `/my/records` 확정 기록·보고·만족도, `/my/sharing` 정보 공유 동의 |

병원은 재활 처방을 승인하고 NPIUM이 최종 매칭을 통제합니다. 치료사의 수락만으로 담당자를 교체하지 않습니다. 신규 매칭은 면허·경력·이력·보험 확인 근거, 보험 유효기간, 배정 보류를 확인합니다. 월간 평가에서 배정을 보류해도 기존 환자의 방문을 자동 중단하지 않습니다.

원문 네 단계는 퇴원 전 연계 → 초기 방문 평가 → 방문 운동 치료 → 데이터화 및 병원 리포팅입니다. 처방은 주 1~3회 중 병원이 정하고 종료일을 직접 입력합니다. 회당 50~60분은 제안서의 운영 기준으로 사용합니다. 초기 처방 승인에는 아직 없는 월간 보고서·외래 재평가를 요구하지 않습니다.

## 팝업과 상세 페이지

관리 대상 선택, 역할 선택, 서비스·지역 필터, 공유, 일정 변경 요청, 매칭 확정·취소 같은 짧은 선택·확인은 현재 화면 위의 팝업으로 처리합니다. 관리 대상을 선택하면 팝업이 닫히고 같은 화면의 대상만 바뀝니다. ESC·닫기·바깥 영역 클릭으로 닫을 수 있으며 닫은 뒤 배경 스크롤과 초점을 복원합니다.

환자별 전체 진행, 회차 보고서 작성·정정, 초기·중간·종료 평가, 보고서 확인·외래 재평가, 재활 처방 승인, 리포트 취합·제공, 치료사 매칭 후보 비교, 청구 이력·금액 조정처럼 정보가 많은 화면은 상세 페이지로 엽니다. `view`·`item` 쿼리에 화면과 대상 식별자를 기록하고, 보호자 보고서는 `subject`로 대상도 유지합니다. 새로고침·브라우저 뒤로 가기·이전 화면 이동을 지원하며 환자 상세 내용은 URL에 넣지 않습니다.

2026-10-15 화면 검증: 상세 페이지 20개와 새로고침, PC·모바일 팝업 선택·닫기 및 페이지 왕복 등 22개 동작을 독립 브라우저에서 확인했습니다. 현재 확인용 체험 서버는 `http://127.0.0.1:3107`입니다. 로컬 DB·로그인 모드의 기본 실행 포트는 위의 3100입니다.

## 보고·승인·정산의 보존 규칙

- 작성 중 회차 기록은 누락을 해결한 것으로 세지 않습니다. 서버의 병원·보호자 조회에도 포함하지 않습니다.
- 참여 상태 정정은 누적 회차를 차이만큼 조정하고 이전 원기록·작성자·사유·시점을 보존합니다.
- 병원에 제공한 보고서는 환자·확정 회차·평가를 제공 당시 데이터로 보존합니다. 이후 원기록 정정으로 기존 제공본을 바꾸지 않습니다.
- 정정은 새 버전으로 작성하고 재검토해 제공합니다. 이전 버전의 담당의 확인·재평가·승인 참조를 보존합니다.
- 보고서 열람, 담당의 확인, 외래 재평가, 변경안 저장, 재활 처방 승인, 치료사 확인, 실제 회차 반영은 서로 별개의 기록입니다. 재평가 저장만으로 처방을 바꾸지 않습니다.
- 처방은 승인 버전·적용일을 보존하며 회차 날짜에 맞는 버전을 연결합니다. 현재 담당 치료사가 해당 버전을 확인해야 그 버전의 회차를 확정할 수 있습니다. 오래된 변경안과 중복 승인·최종 매칭을 차단합니다.
- 청구 발행 시 계약·회차·금액을 고정합니다. 이후 단가나 참석 기록이 바뀌면 검토 필요 상태를 표시합니다. 금액 변경은 별도 조정 금액·사유·담당자·시점으로 기록합니다. 조정은 세금 포함 원 단위이며 외부 세금계산서 수정 발행을 뜻하지 않습니다.
- 치료사별 회차 통계는 실제 원기록 작성자를 기준으로 집계합니다. 기능 변화는 동일 측정 조건과 비교 가능 표본·제외 분모를 표시합니다. ROM·근력은 같은 항목·좌우의 초기/후속 평가를 비교합니다. 서로 다른 만족도 척도는 한 평균으로 합치지 않습니다.

## 저장 구조와 검증

`src/lib/repo/engine.ts`가 체험·서버 공통 업무 규칙을 처리합니다. 브라우저 저장과 서버 API는 각각 `local-repository.ts`, `server-repository.ts`로 분리되어 있습니다. 서버는 SQLite의 상태와 변경 번호를 트랜잭션으로 저장하고, 오래된 변경 번호의 요청은 409로 거절해 재확인을 요구합니다. 5초 간격으로 최신 상태를 조회하며 저장 실패 시 입력을 유지하고 오류를 표시합니다.

`src/lib/server/authorization.ts`는 역할·기관·담당 관계·채팅 참여·원기록 작성자를 요청마다 검사합니다. 작성자·승인자 표시 값은 클라이언트 요청 대신 서버 세션으로 결정합니다. 관리자 전체 조회, 병원 자기 기관 조회, 치료사 담당·제안 및 본인 작성 이력, 환자 연결 대상 조회를 구분합니다.

```powershell
npm test
npm run lint
npm run build
npm run local:build
```

2026-10-15 검증: 업무·API 회귀 테스트 12개 통과, 체험/서버 빌드 통과. 독립 브라우저에서 체험 24개 화면과 서버 로그인 후 24개 화면을 확인했습니다. 병원 제공본 확인→외래 재평가→변경안 저장·승인→치료사 확인→승인 버전을 연결한 회차 확정도 실제 UI로 검증했습니다. 테스트 DB는 `test-results`에 격리합니다.

## 현재 연결 범위

로컬 서버·DB·로그인·내부 업무 처리는 구현했습니다. 병원 전산 API, 외부 기관의 면허·보험 자동 검증, 실제 서류 파일 업로드, GPS 수집, 결제·세금계산서·문자/푸시 발송, 연구·보험 기관으로의 외부 제출과 운영 배포는 연결하지 않았습니다. 인증 자료는 담당자가 검토한 문서 식별정보·확인 경로를 기록하는 방식입니다. 보고서 제공은 앱 안에서 해당 병원 계정에 제공하는 처리이며 외부 병원 시스템으로 전송하는 처리가 아닙니다. 공개 탐색 페이지의 전문가·후기·공간은 예시 콘텐츠입니다.

주 제안서 항목과 후속 합의에 따른 구현을 구분하며, 실제 임상 효과·계약·기관 인증이 검증됐다고 표현하지 않습니다. 로컬 실행 준비는 실제 의료기관 운영 배포 완료를 의미하지 않습니다.
